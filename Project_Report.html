1. Project Overview

Bhawalpur Foods is a full-stack restaurant web application built for Bhawalpur Foods — Biryani Point & Restaurant, a desi cuisine restaurant established in 1990 and operating across multiple branches in Bahawalpur, Pakistan.

The application serves three user groups simultaneously:

  • Customers — browse the menu, build a cart, and place orders via WhatsApp or online card payment (Stripe).
  • Admins — manage the food menu (add, edit, remove items) and track/update order statuses through a dedicated dashboard.
  • Visitors — learn about the restaurant, find branch locations, and contact the team.
Key differentiator: Orders can be placed through two channels — a pre-filled WhatsApp message (no account needed) or a secure Stripe hosted checkout for card payments. Both channels record the order in the database for admin tracking.

3.1 Data Flow

  • Both frontend and admin call the same backend REST API.
  • The backend URL is hardcoded in frontend/src/context/StoreContext.jsx and admin/src/App.jsx.
  • MongoDB stores users, food items, orders, and cart data.
  • Uploaded food images are stored on disk in backend/uploads/ and served as static files at /images/:filename.

4.4 Cart Flow

There is no dedicated /cart page. The cart is a slide-in drawer:

5. Payment Gateway Integration (Stripe)

Important for Pakistan: Stripe does not support Pakistan as a live merchant country — Pakistani businesses cannot receive payouts to local bank accounts via Stripe directly. The integration works perfectly in test mode for development and demos. For a live production setup in Pakistan, consider JazzCash or EasyPaisa.

5.1 Complete Payment Flow

1
User fills the OrderCheckout form and selects Pay Online.
2
Frontend validates all required fields, then POSTs { items, amount, deliveryFee, address } to POST /api/order/stripe.
3
Backend pre-generates a MongoDB _id, creates a Stripe Checkout Session with that ID embedded in the redirect URLs, then saves the order to the database with the stripeSessionId.
4
Backend returns { session_url }. Frontend redirects: window.location.href = session_url.
5
User completes payment on Stripe's secure hosted checkout page.
6
Stripe redirects to /verify?success=true&orderId=<id> (or success=false on cancel).
7
PaymentVerify page POSTs { orderId } to POST /api/order/verify.
8
Backend retrieves the order, calls stripe.checkout.sessions.retrieve(order.stripeSessionId), and checks payment_status === "paid" directly with Stripe — does not trust the URL parameter.
9
If paid: marks order.payment = true, clears user cart → returns success. If not paid: deletes the pending order → returns failure.
10
Frontend shows success or failure screen with navigation options.

5.2 Security Considerations

  • The order is saved to the database only after the Stripe session is successfully created — no orphan records if Stripe fails.
  • Payment verification uses the Stripe API directly — the success=true URL parameter is never trusted alone.
  • The stripeSessionId is stored on the order and used for server-side verification.

6.2 Edit Food Item Feature

The Edit page (/edit/:id) was added to allow admins to update food item details without having to remove and re-add the item. It works as follows:

  • Admin clicks the ✏️ Edit button on any row in the List page.
  • The Edit form loads with the item's current name, description, category, price, and image pre-filled.
  • The image is optional to change — if no new image is uploaded, the existing image is kept.
  • If a new image is uploaded, the old image file is deleted from backend/uploads/ and the new one is saved.
  • Clicking SAVE CHANGES sends a POST /api/food/update request and returns to the List page.
  • Clicking CANCEL returns to the List page without saving.

7.3 Authentication Pattern

  • JWT token is sent in the request header as headers.token (not Authorization: Bearer).
  • authMiddleware verifies the token and injects userId into req.body.
  • Admin verification is done inside each controller by querying user.role === "admin" — not in middleware.
  • Public endpoints (/api/order/stripe, /api/order/verify) do not use authMiddleware but still check req.body.userId if a token was optionally provided.

10. Development Setup & Running the Project

10.1 Prerequisites

  • Node.js v18 or higher
  • MongoDB running locally (mongod) or a MongoDB Atlas connection string
  • A Stripe account with a test secret key

10.2 First-Time Setup

# 1. Install dependencies for all three apps
cd frontend  &&  npm install
cd ../admin  &&  npm install
cd ../backend && npm install

# 2. Create backend/.env (see Section 9)

# 3. Seed sample food items (optional — for local demo)
cd backend
node seed.js

# 4. Create admin user
node createAdmin.js
# Output: admin@bhawalpur.com / admin1234

Update the backend URL in two files when switching environments:

Also update FRONTEND_URL in backend/.env to match the deployed frontend URL.
